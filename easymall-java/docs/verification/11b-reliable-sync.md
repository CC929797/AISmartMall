# 11B 商品搜索、知识库与订单延迟任务验收

## 代码和数据库

- 商品保存、上下架、删除与 FAQ 新增、编辑、删除，在原业务事务内更新 `search_sync_state` 并写入 `business_task`。确认收货带来的销量变化只更新商品关键词索引。
- `PRODUCT_SEARCH`、`PRODUCT_VECTOR`、`FAQ_VECTOR` 由 Web 的搜索同步 Worker 执行。每个同步目标独立发布版本，关键词索引和向量索引可以分别恢复。新版本未发布时，相应商品或 FAQ 可能暂时从搜索或推荐结果中消失，搜索总条数随索引刷新收敛。
- `ORDER_PAID`、`ORDER_LOGISTICS_STEP`、`ORDER_AUTO_CONFIRM` 由 Web 的履约 Worker 执行。发货时保存首条物流并登记后续任务，第一条模拟更新延迟约 10 秒，后续每跳约 1–5 秒另加调度延迟。自动收货从发货开始按 `order.confirm.minute` 计时。`logistics.mode=simulated` 时运行，暂停模拟时已登记的模拟任务延期，恢复后继续。
- 步骤 09 的退款查证和步骤 10 的主动查单、取消和超时关单继续依靠各自的数据库定时补偿。`ORDER_CREATED` 和 `ORDER_CANCELLED` 是已写入的业务事件，两类任务目前没有处理器，保持 `READY` 属于预期。
- 本步骤只创建 `search_sync_state`。数据库先具备 [11A 任务表](../../db/migration/V20261107_01__business_task.sql) 及步骤 08–10 已部署的结构，在目标环境执行一次 [11B 迁移 SQL](../../db/migration/V20261122_01__search_sync_state.sql)，执行 `SHOW CREATE TABLE search_sync_state;` 核对。应用启动不会自动执行迁移。

## 切换和旧队列

1. 暂停写入，停止所有旧版 Admin、Web 及旧消费者，避免新旧实例同时生产和消费。按上节执行 SQL，再启动新版 Admin、Web 和管理端前端。Web 已内置本次真实业务处理器。
2. 登录管理端，打开「小工具」，展开「迁移与存量补同步」，每次点击「迁移一批旧队列」。核对返回的 RAG、物流、自动收货数量，三项都为 0 时结束。任务先提交 MySQL，再移除对应 Redis 成员。出错的队列头仍保留，修复数据或连接后继续。
3. 同步存量商品时选择「商品」，点击「同步所有商品」。提示「还有商品未同步」时继续点击，直到提示「所有商品同步任务已提交」。同步 FAQ 时选择「FAQ」，点击「补同步一批 FAQ」直到返回 0 条。页面会自动填写下一批的游标。

## 手工验收用例

| 用例 | 怎么操作 | 预期结果 |
|---|---|---|
| 商品同步 | 在管理端新建或修改一件测试商品，用易辨认的名称保存，上架。到小工具按商品 ID 查任务，再从商城按名称搜索并向 AI 导购询问该商品。随后修改名称并快速下架。 | 每次商品变更产生对应版本的 `PRODUCT_SEARCH` 和 `PRODUCT_VECTOR`，正常时最新任务变为 `SUCCESS`。搜索和导购最后均看不到已下架商品。 |
| FAQ 同步 | 新建一条带唯一关键词的问题。任务成功后在商城询问，修改答案后再问，最后删除 FAQ。每一步开启新会话避免对话历史干扰。 | `FAQ_VECTOR` 有对应版本。修改后使用新答案，删除后检索上下文中没有旧 FAQ。模型措辞可变化，任务和版本记录更适合判断同步结果。 |
| 服务失败和恢复 | 在测试环境停掉 ES，或让 Embedding 请求失败。保存测试商品或 FAQ，在小工具查询其任务。恢复服务，若任务已经变为 `DEAD`，点击「重试」。 | MySQL 业务保存仍成功。故障中的任务可见为 `RETRY` 或 `DEAD`，有尝试次数和简要错误。恢复后最新版本发布，任务为 `SUCCESS`。 |
| 执行时重启 | 在测试环境放慢 Embedding，等任务进入 `RUNNING` 后终止 Web，再重启并观察同一任务。 | 未到期租约在超时后可重新领取。任务恢复后发布一次有效版本，途中已写入的旧向量不会被作为新版本引用。 |
| 模拟物流与自动收货 | 在 Web 配置 `logistics.mode=simulated`，保留现有自动发货设置。支付一笔沙箱订单并记下商城订单号。在「小工具」按订单号查看物流和自动收货任务，发货后、首条模拟轨迹前重启 Web。 | 重启后继续推进，轨迹总数 6 条，包含首条发货和最终已送达。过了从发货计算的自动确认时间后，订单为「已完成」且销量只加一次。也可用另一笔订单先手动确认，届时自动任务应无重复效果。 |
| 旧 Redis 任务 | 在测试环境用旧版留下未消费的 FAQ 或物流任务，按上节切换，再重复提交一批迁移。 | 原有业务和进度保留，已完成任务不会产生重复物流轨迹或重复加销量，最后三项迁移计数均为 0。 |
| 支付与退款回归 | 复测步骤 10 的已付款、取消确认、超时关单，以及步骤 09 的部分退款或全额退款。 | 付款、关单、退款状态及库存处理沿用原来的业务规则。 |

只读查询示例，修改示例值后执行。商品任务使用商品 ID，FAQ 使用数字 ID，模拟物流与收货使用商城订单号，`ORDER_PAID` 使用支付单号。

```sql
SET @biz_key = '你的业务编号';

SELECT task_type, biz_key, requested_version, published_version, updated_at
FROM search_sync_state
WHERE biz_key = @biz_key
ORDER BY task_type;

SELECT task_type, biz_key, biz_version, status, attempts, next_run_at, last_error
FROM business_task
WHERE biz_key = @biz_key
ORDER BY created_at, task_type;

SELECT COUNT(*) AS logistics_record_count
FROM order_logistics_info_record
WHERE order_id = @biz_key;
```

对搜索和 FAQ，正常收尾后需看到 `requested_version = published_version`。旧版本若已被新版本取代，可以结束为 `SUCCESS`，有效版本以 `search_sync_state` 为准。
