# 步骤09 退款单与状态机

2026-11-14，步骤09已实现。隔离 MySQL 集成、定向回归和两套前端构建已通过。支付宝沙箱单笔「部分退款 → 剩余商品发货 → 确认收货」用例已通过商城数据库核对。

## 修改原因

- 原退款代码把明细的旧状态写进了主订单对象，明细更新条件缺少旧状态校验。两次请求都可能读到「正常」，进而各自向支付宝发起退款。
- 原实现把支付宝调用放在数据库事务中。若渠道已退款而回包丢失，或后续本地写入失败，数据库回滚无法撤销渠道资金变化。重新生成退款号又会让渠道收到一笔新的退款请求。
- 主单状态由明细汇总得出。同一主单的不同明细并发退款，以及退款与发货交错时，需要按当前数据库状态确定主单结果和库存处理。

## 实现

1. 事务 A 锁定主订单，校验归属、状态和明细金额。明细旧状态为 `NORMAL` 时才允许改为 `REFUNDING`，并插入 `PROCESSING` 退款单。金额取自 `order_item.item_amount`，按整条明细全额退款。
2. 提交事务后调用 `alipay.trade.refund`。`refund_request.channel_request_no` 对应渠道的 `out_request_no`，生成后固定。`(user_id, request_id)` 保存原请求的结果，同一明细的有效退款还受独立唯一键约束。
3. 事务 B 以退款单版本和明细旧状态为条件落库。成功时更新明细和主单，待发货明细归还一次库存。渠道明确拒绝时置为 `FAILED` 并释放明细；同一请求号仍能读到该次失败。结果待确认时置为 `UNKNOWN` 并保留占用。
4. 商城 Web 服务定时扫描到期的 `PROCESSING`、`UNKNOWN`。单次最多取 5 条，每轮间隔 15 秒，退款单最早在当前处理约 60 秒后可重新领取。补偿先按原支付单号和退款号查证，确认未找到退款明细时才用原退款号发起重试。查询与重试使用支付宝退款接口的原请求编号。 [支付宝退款接口](https://developer.alibaba.com/docs/doc.htm?articleId=106384&docType=1&treeId=318)
5. 发货、确认收货和退款使用同一主单行锁。退款待确认时暂缓履约，模拟发货或自动确认任务遇到此情况会延迟重试。部分退款后，待发货或待收货列表根据物流状态继续展示剩余商品。历史明细的已退款状态仍会显示退款成功。

用户端通过 `POST /api/order/refundOrder` 提交 `orderItemId` 和 `requestId`。退款单的 `status` 用于展示处理中、待确认、成功或失败。`POST /api/order/getRefundStatus` 按当前用户和明细读取商城最近的退款状态，点击查询不会向支付宝发起新的退款。失败后允许用户发起一次新请求，待确认时保留原请求号。

## 数据库迁移

在运行商城的 MySQL 8.0.16 或更高版本中，选中商城服务实际连接的数据库，执行 [V20261114_01__refund_request.sql](../../db/migration/V20261114_01__refund_request.sql) 一次。脚本只创建 `refund_request`，旧表与旧退款无需变更或回填。应用启动时不会自动建表。迁移后重新启动使用新代码的后端，并同步更新用户端和管理端。

```sql
SELECT DATABASE();
SHOW TABLES LIKE 'refund_request';
```

同名表已存在时，先通过 `SHOW CREATE TABLE refund_request` 核对列、状态约束和唯一键。脚本已在隔离测试库验证。2026-11-14 复查时，开发库 `easymall2` 已具备 `refund_request` 并保存了该笔测试退款。

## 验证记录

MySQL 8.0.43 隔离库使用真实 SQL 和事务，Redis 与支付渠道使用测试替身。51 项定向用例通过，其中包含 8 项退款集成测试、22 项下单集成回归、21 项权限和支付网关测试。另有 568 项后端常规测试、76 项前端测试及两套前端生产构建通过。常规测试在允许访问本机回环端口和创建临时目录链接后复跑通过，Mockito 通过 JVM 启动参数加载。

| 场景 | 验证结果 |
|---|---|
| 同一明细并发和重复请求 | 共享一条有效退款，渠道只调用一次，库存只归还一次 |
| 超时后查证未发现退款 | 查证和重试都复用原退款号，最终只保留一条退款单 |
| 渠道成功但本地写入失败 | 明细保留待确认，查询原退款号后补写成功，本次只调用一次退款 |
| 同一主单的两条明细并发退款 | 最后一条成功后主单汇总为全部退款，两条库存分别归还 |
| 已发货退款和越权访问 | 已发货退款不自动入库，另一用户无法发起或读取退款 |
| 渠道明确拒绝 | 释放明细，原请求重放仍为失败，新请求可重试 |
| 部分退款与剩余商品履约 | 未决时暂缓发货，退款确认后剩余商品可发货和确认收货 |
| 历史退款明细 | 已退明细没有新表记录时也不会再次调用渠道退款 |

### 手动复测步骤

1. 选择一笔已付款且未确认收货的沙箱订单，在「我的订单」点击某条明细的「退款」。核对退款金额与该条明细实付金额相同。
2. 若页面显示「退款结果待确认」，使用「查询退款结果」观察状态。用同一个 `pay_order_id` 和 `channel_request_no` 在支付宝核对退款状态和金额。
3. 用同一个 `requestId` 重放请求，核对退回的 `refundId` 和退款金额一致。分别检查未发货时库存仅归还一次、已发货时 SKU 库存保持原值。
4. 多明细订单可选同一商品的两个规格。先退一条并检查主单「部分退款」，另一条仍可履约。若两条均退款成功，检查主单「已退款」。

```sql
SELECT refund_id, order_item_id, pay_order_id, channel_request_no,
       amount, status, version, last_error, next_check_at
FROM refund_request
WHERE order_item_id = '<待核对明细编号>'
ORDER BY created_at DESC;
```
