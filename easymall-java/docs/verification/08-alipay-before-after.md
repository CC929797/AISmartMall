## 只读对照验证

诊断代码仅放在忽略的 `runtime/diagnostics/`，不参与正式业务运行。没有创建新交易、发起付款、退款、关单或更新数据库。

1. 当前依赖 + 本次报错订单：返回 `code=20000`、`sub_code=aop.ACQ.SYSTEM_ERROR`。
2. 同一 SDK + 旧 BC 1.62 + 同一报错订单：返回相同错误。该测试只替换了诊断进程的 BC 依赖，并未回退商城依赖或运行完整旧版商城。
3. 当前依赖 + 从10月24日成功日志中提取的旧已付款订单：现在也返回相同错误。
4. 私钥与应用证书匹配、应用 ID 与证书匹配、证书有效、本机时间与沙箱服务器时间一致。

这些结果说明，当前后台查单错误不只发生在步骤08创建的新订单上；旧版 BC 依赖也没有恢复正常响应。现有证据把排查重点指向当前沙箱服务或该沙箱应用的状态，仍无法仅凭通用错误码确定平台内部的具体原因，也不能断言所有沙箱用户都受影响。

收银台页面的 SYSTEM_ERROR 与后台查单错误是两个接口的现象，不能只凭错误名称断言二者内部原因相同。

## 与 postOrder 修复的关系

此前 postOrder 持续 PROCESSING 是新增幂等逻辑没有隔离 MyBatis 会话缓存造成的本地缺陷，已在 [postOrder 修复记录](08-postorder-processing-fix.md) 中说明并验证。当前页面已能进入支付宝收银台，不应把两次故障合并为同一个原因。

当前云排查页面没有提供可选服务，并有账号授权提示，不能据此断言沙箱配置错误。若该账号无法使用查询工具，可向支付宝官方技术支持提供接口、时间、错误码及 trace_id，请平台核查对应沙箱应用；保留应用私钥和完整签名。
